# fix: ensure OfflineQueueBanner always shows live pending count

## Summary

The `OfflineQueueBanner` component displays the queue's pending item count and processing status to players on unreliable connections. However, the count was derived from React state that only updated on specific triggers (mount, enqueue, manual retry), causing the banner to show stale data when items completed while mounted.

For a player relying on this banner to know whether their registration/update actually went through, seeing outdated counts undermines trust in the entire offline-queue feature.

This PR adds a polling mechanism in `useOfflineQueue` that keeps the UI fresh by re-fetching counts every 2 seconds while there's something to display.

## Changes

### `hooks/useOfflineQueue.ts`

- Added a new `useEffect` hook that:
  - Polls for queue updates every 2 seconds when `status === 'processing'`, `pendingCount > 0`, or `failedCount > 0`
  - Calls `refreshCounts()` during each poll cycle to sync with IndexedDB state
  - Runs an immediate poll on mount, then at the 2s interval
  - Clears the interval on unmount

### `components/player/OfflineQueueBanner.tsx`

- No changes - component already correctly displays whatever props it receives

### `__tests__/components/player/OfflineQueueBanner.test.tsx`

- Added new test suite `OfflineQueueBanner live count updates` with three tests:
  - Verifies displayed count updates when an item completes (simulated via re-render)
  - Verifies banner hides when count reaches 0
  - Verifies processing state shows and retry button hides during `isProcessing`

## Background

Players on low-bandwidth connections are the primary audience for this offline queue feature. The banner is their primary feedback mechanism for understanding:

1. Whether their changes were saved locally (queued)
2. Whether the system is actively trying to submit them (processing)
3. When their changes have actually been flushed (banner disappears)
4. Whether any actions permanently failed and need manual cleanup

A banner that lags behind reality (e.g., showing "2 pending" after one has already succeeded) erodes user confidence that the feature is working as intended.

The polling approach was chosen over:
- **Immediate revalidation after every IndexedDB operation**: Too invasive, would require modifying `offlineQueue.ts` and adding callbacks throughout
- **IndexedDB `versionchange` events**: Complex to coordinate across tabs/processes, doesn't help with same-tab changes
- **Manual refresh only**: Too brittle, relies on user action (retry button click) to get fresh data

2 second polling provides a good balance: fresh enough for UX while not overloading IndexedDB or causing UI thrash.
