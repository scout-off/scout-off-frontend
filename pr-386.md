# fix: normalize Stellar addresses in watchlist to prevent case-sensitivity duplicates

## Summary

Stellar public keys can be represented with different casing in some contexts. The watchlist implementation was not normalizing addresses before using them as lookup/dedup keys, which could allow the same player to be added to a watchlist twice under differently-cased references, or cause 'already in watchlist' checks to fail when they should have matched.

This PR adds address normalization at every write and read boundary in the watchlist store and API, ensuring all addresses are stored and compared in uppercase (matching Stellar's standard G... key format).

## Changes

### `lib/stellar.ts`

- Added `normalizeStellarAddress(key: string): string` function that:
  - Validates the key is a valid Ed25519 public key using `StrKey.decodeEd25519PublicKey()`
  - Re-encodes using `StrKey.encodeEd25519PublicKey()` which returns uppercase
  - Throws if the key is invalid
- Already had `isValidStellarAddress(key: string): boolean` for pre-validation

### `lib/watchlistStore.ts`

- Imported `normalizeStellarAddress` from `@/lib/stellar`
- Modified `add(scoutWallet, playerId)` to normalize **both** addresses before storage
- Modified `remove(scoutWallet, id)` to normalize `scoutWallet` before lookup
- Modified `clearForWallet(scoutWallet)` to normalize `scoutWallet` before deletion
- Modified `list(scoutWallet)` to normalize `scoutWallet` before querying

### `app/api/watchlist/route.ts`

- Imported `normalizeStellarAddress` and `isValidStellarAddress` from `@/lib/stellar`
- Added validation in `POST` handler to reject non-Stellar addresses with 400
- Added normalization of `playerId` before passing to `WatchlistStore.getInstance().add()`

### `__tests__/lib/watchlistStore.test.ts`

- Added new test suite `WatchlistStore address normalization` with three tests:
  - Verifies player addresses are normalized to uppercase before storage
  - Verifies scout wallet addresses are normalized to uppercase before storage  
  - Verifies same address with different casing is treated as a duplicate (not two entries)

### `__tests__/api/watchlist/route.test.ts`

- Added new test suite `POST /api/watchlist address validation and normalization` with five tests:
  - Verifies invalid playerIds are rejected with 400
  - Verifies short addresses are rejected with 400
  - Verifies lowercase playerIds are normalized to uppercase before storage
  - Verifies mixed-case playerIds are normalized to uppercase before storage
  - Verifies same address added twice with different casing results in only one entry

## Security Impact

**High** — This fixes a class of bug where:

- Same Stellar address with different casing (e.g., `G...` vs `g...`) could create duplicate watchlist entries
- "Already in watchlist" checks could fail when they should have matched
- Most real-world Stellar SDK usage already returns consistently-cased keys — the risk shows up specifically with manually-typed or copy-pasted address input paths

The fix ensures that all addresses are stored and compared in uppercase, preventing these edge cases entirely.
